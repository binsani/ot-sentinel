# Release checklist

This checklist separates engineering readiness from site acceptance and independent assessment.
A software release may be published when its engineering gates pass, but it must not be described
as field-accepted, externally audited, or certified without the corresponding signed evidence.

## Release candidate

- [ ] Version matches backend, sensor, frontend, API, exports, Kubernetes images, changelog, and tag.
- [ ] Backend, sensor, frontend, container, migration, backup/restore, CodeQL, and passive-release
      checks pass on the release commit.
- [ ] The default 10,000-asset performance workflow passes and its JSON artifact is retained.
- [ ] All external PCAP fixtures download from immutable commits and match the manifest SHA-256.
- [ ] Python wheels, frontend bundle, container images, SBOM/provenance attestations, and
      `SHA256SUMS` are generated by the tag workflow.
- [ ] The audit-evidence manifest is generated from the clean release commit and retained.
- [ ] Release notes state known limitations, upgrade requirements, and passive-only safety status.
- [ ] No secrets, plant identifiers, completed field records, or sensitive captures are included.

## Publication

1. Merge the release-preparation pull request after all protected checks pass.
2. Confirm main is clean and the intended commit is recorded in the approval.
3. Create the signed or annotated `v1.0.0` tag only after explicit release approval.
4. Verify the tag workflow publishes all three container images and the GitHub release artifacts.
5. Download `SHA256SUMS` and independently verify at least one wheel and the frontend archive.
6. Preserve the workflow URL, release URL, commit, tag signature result, and audit manifest.

## Deployment boundary

Publishing v1.0.0 does not authorize production installation. Each site must complete the field
acceptance procedure using its controlled record. External assessment remains open until an
independent assessor issues a final report and findings are dispositioned.
